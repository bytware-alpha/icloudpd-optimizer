# Architecture review — 2026-11-25

Reviewed `cursor/merge-deletion-guards-into-per-photo` at `e452646` (PR #2), which is `main` at `b86bdea` plus the deletion-guard merge. Review only. `auto_delete` stays false. This change adds this document and nothing else.

The outcomes behind C1–C6 and an external delete gate are right. Building them as six features is not. The binary already contains two schedulers, three session files, a manual Shared Library detour, and a one-shot migration larger than the live pipeline. Collapse to one index, one session, one four-stage pipeline, and one gate that is not part of the pipeline.

## (a) What to delete or consolidate

In impact order.

1. **Two live schedulers.** `run_monitor_once` runs `run_lifecycle_stages` when `rolling_lifecycle` is false and `run_rolling_lifecycle_passes` when it is true. Both upload (`upload_verified_heics` vs `run_rolling_asset_upload`), both resolve originals, both delete. Keep one queue-based pipeline. Delete the other once the queue exists. Do not keep both "for safety."

2. **`src/legacy_upload_migration/` (~24k lines: `apply.rs`, `evidence.rs`, `tests.rs`).** One cohort of already-uploaded HEICs, with its own copy of upload, mirror, quarantine, and delete. Do not thread C1–C6 through it. After that cohort is confirmed complete, stop compiling it into the hot binary.

3. **`photos_import_handoff`.** `stage_verified_heic_for_photos_import` records `import_lands_in = personal_library` and tells a person to use Image > Move to Shared Library. `ensure_upload_dispatch_allowed` then refuses the CloudKit upload. That path cannot put a HEIC in the library the original lives in. The upload client already targets a zone. Delete the handoff.

4. **Three session files, one cookie jar.** `refresh_optimizer_sessions.prepare_export` writes `upload-session-production.json`, `delete-session-production.json`, and `delete-session-shared-production.json` from one pyicloud login. Cookies and `ckdatabasews_url` are shared. The shared file keeps the previous `database_scope`, `zone_name`, `owner_record_name`, and query params. `sharedlibrary_url` is written and never read by Rust. `CloudKitDeleteSession` stores one zone, and `validate_session_destination` rejects any other zone. `MonitorConfig` has one `delete_session_path`. That is why the shared lane 421s on a snapshot that looks refreshed. `UploadSession` is already zone-free; the destination is an argument. Make the read/delete session the same shape.

5. **Path-shaped asset ids and permanent NAS verdicts.** `monitor_asset_id` hashes the path relative to `download_root`. `discover_raw_asset` refuses any state other than `Discovered`. The scan in `run_monitor_once` skips `Converted` and every later state, including `Failed`, `NoAction`, `NeedsReview`, and `Deleted`. A file that leaves the NAS stays in the manifest. An iCloud asset icloudpd never wrote never appears. The key has to be `(zone, recordName, resource field)`.

6. **Date-window identity scan as the steady state.** `resolve_original_asset` seeks `CPLAssetAndMasterByAssetDateWithoutHiddenOrDeleted` with `seek_original_asset_query_page`, then `download_resource`s every size match and compares SHA-256. `getCurrentSyncToken=True` is sent and the returned token is not stored. `adjusted_source::lookup_exact_record` already fetches one record by name. That is the steady-state read. The ranked date query is the nightly fallback, and it must not download bodies.

7. **Self-approval inside the monitor.** `prepare_delete_item` calls `mark_delete_eligible` and then `approve_delete` with `delete_operator` whenever `auto_delete` is on, before the live HEIC check. Approval cannot be a string in `MonitorConfig`.

Leave `smb_noreplace`, the mount check in `ensure_delete_nas_mount`, and `operation_hold` alone. They are not the pipeline. Do not grow them while building the index.

`monitor.rs` is about 26k lines, of which the tests start near line 12077. `cli.rs` is about 15k, much of it migration and one-shot commands. The win is deleting the second scheduler and the migration, not splitting files.

## (b) Simpler design

One row per remote resource, not per NAS path:

`zone, owner, recordName, resource field, remote size, remote fingerprint, local sha256, heic sha256, uploaded recordName, readback sha256, stage`

Stages are only `missing`, `have_raw`, `have_heic`, `upload_intent`, `uploaded`, `readback_ok`. Delete is not a stage.

```
per-zone changes (token)  -->  index
        | nightly full query if the token is missing or rejected
        v
download queue   encode queue   upload queue   readback queue
(only missing    (largest       (same zone as  (size + SHA-256
 RAW resources)   first, all     the row)       of the new asset)
                  cores)
```

C1 and C2 are this index. The work list is "resources in the index whose bytes are not local," not "files icloudpd happened to write." `record_original_asset_resources` already walks `resOriginal`, `resOriginalAlt`, `resSidecar`, and `resOriginalVidCompl`. `lookup_exact_record` is the per-record read. Do not add a third downloader.

C5 is the session object: cookies, dsid, service URLs, expiry. Zone and owner are arguments, as they already are on `upload_verified_source_to_library`. On expiry or HTTP 421, refresh once and stop the pass. Do not keep a shared snapshot.

C3 is three numbers on the HTTP client plus a classifier in `read_json_response_body`. It is not a new lifecycle.

C4 is a sort of the encode and upload queues by raw size. It is not a scheduler.

C6 is one column, `upload_intent`, written before `putAsset`. On resume, look up that zone for an active asset with that HEIC SHA-256 and adopt it. `create_upload_url_payload` mints a new UUID on every call, so the server upload id cannot be the resume key. `parse_put_asset_response` already adopts HTTP 409 `"duplicate photo found"`. That only helps if the retry reaches `putAsset` and Apple still calls it a duplicate. A re-encoded HEIC will not.

The gate is a separate file, mode `0600`, with an expiry and the record names it covers. The monitor process must not be able to refresh it. `isDeleted` is sent only when that file names the record, it has not expired, every RAW-typed resource of that asset is in the index with a local SHA-256, and `remote_readback` matches. Otherwise do nothing. `auto_delete` stays false, and `prepare_delete_item` must stop calling `approve_delete`.

## (c) Parallelism and a real wall clock

Today the caps stack:

| Cap | Where | Effect |
|---|---|---|
| `jobs = 1` | `MonitorConfig::new` | Default concurrency is 1 |
| `max_lifecycle_per_scan = 5` | `default_max_lifecycle_per_scan` | At most 5 assets advance per scan |
| `scan_interval_seconds = 300` | `MonitorConfig::new` | A full pass of 8,400 assets is 1,680 scans |
| `MAX_ROLLING_NETWORK_SLOTS = 2` | `monitor.rs` | Hard ceiling, not config |
| `upload_slots = jobs.clamp(1, 2)` | `upload_verified_heics` | With `jobs = 1`, uploads are serial |
| Status poll inside the slot | `poll_until_upload_complete` | Up to 120 polls, 1s apart, while holding the network permit |
| Child process per upload | `run_upload_proof_*_child_*` | Reloads the session and rehashes the HEIC |
| Resolve downloads the RAW | `resolve_original_asset` | Re-fetches a file already on disk to learn its record id |

`8,400 / 5 * 300s` is about 140 hours of scan spacing before any byte moves. New discovery is skipped while that backlog is full (`new_monitor_work_skip_reason`). The machine is not the bottleneck.

Use four pools. Do not let one global slot cover all of them.

- **Download** (resource URLs, CDN): 8–12. This is not the CloudKit database API.
- **Encode**: one process per core. The embedded-preview recipe (`exiftool` extract, `sips` or `heif-enc`) is short. `rolling_lifecycle_convert_stage_jobs` defaulting to half the CPU is the wrong direction. Drop the child-per-upload once the in-process client is the only uploader; the child exists to isolate a crash, and an intent row does that more cheaply.
- **CloudKit query/lookup**: 2–4. This is the API that 429s.
- **Photos upload** (`createUploadUrl`, PUT, `putAsset`): start at 4, hard cap 8. Release the slot before `uploadStatus`. Poll on a separate pool of 8.
- **Readback**: same CDN pool as download, overlapping the next uploads.

Adapt per pool, in `read_json_response_body`, which today turns every non-2xx into `UploadHttpStatus` and stops:

- **429 / 503**: halve that pool, then add one after a window of successes. Do not fail the asset.
- **413**: storage full. Stop uploads. Do not retry and do not shrink the pool.
- **421**: session or partition. Refresh the one session once. If it 421s again, stop the pass. Do not reduce concurrency.
- **401 / 403**: stop.

The rolling uploader does not do this. `run_rolling_asset_upload` only pauses on `provider_auth_rejection_text`, which matches 401 and 403. `upload_error_requires_operator_action` matches `HTTP 421`, and only the batch uploader calls it. Moving to the per-photo path without fixing that will keep sending on a dead shared session.

Wall clock for 8,400 files / 260 GB, assuming the HEIC is the embedded preview (a few MB, so the upload is on the order of 25–40 GB, not 260 GB):

- **260 GB fetch**, only for bytes not already on the NAS. At 30 MB/s aggregate, about 2.5 hours. At 80 MB/s, under an hour. Eight to twelve CDN connections are what gets you there. One CloudKit query connection will not.
- **Encode** of previews: on the order of 10–30 minutes at 8 cores. It hides behind upload.
- **Upload of ~30 GB** at 4 streams. A realistic aggregate is a few MB/s to a few tens of MB/s. Call it 1–4 hours. Measure the first 50 and set the pool from that, not from a guess.
- **Readback** of the same HEICs overlaps upload if it is its own pool. Serial readback doubles the upload time.

So a pipelined run that already has the primary files locally is an afternoon to a day. A run that must also pull 260 GB is still inside a day on a normal home link. The current scheduler is several days of scan spacing even if every asset were instant. Do not re-download a RAW that already has a local SHA-256 just to attach a record id. Treat `resOriginalFingerprint` as an opaque id until its algorithm is proven; do not assume it is SHA-256.

Largest-first belongs on the encode and upload queues so a failure on a big file shows up early. It does not change the total much.

## (d) Same library, same capture date

Placement is already per asset, and then a single session throws it away.

`original_asset_destination` and `upload_destination_for_asset` copy `database_scope`, `zone_name`, and `owner_record_name` from the original proof. `require_matching_library_destination` refuses an upload proof that disagrees. `create_upload_url_payload` and `put_asset_payload` send `zoneName` and, except for private `PrimarySync`, `ownerRecordName`. `validate_library_destination` requires `SharedSync-` plus an owner for shared, and exactly `PrimarySync` for private.

The break is the read side. `resolve_original_asset` queries `session.zone` only. One `delete_session_path` means one library per process. A shared original is invisible to a private session, and a private original 421s against the stale shared file. Fix the session, not the payload. Run the change feed once per zone (private `PrimarySync`, and each `SharedSync-*` with its owner) using the same cookies. The row's zone is the upload destination. No second code path.

`photos_import_handoff` lands in the personal library on purpose. Remove it so it cannot block `ensure_upload_dispatch_allowed`.

Capture date is wrong even after a correct zone upload. The conversion plan copies tags with `exiftool -TagsFromFile -all:all`, which is necessary. `put_asset_payload` then sends `lastModDate` from the HEIC file mtime (`VerifiedUploadSource::open_candidate`) and one `time_zone_offset_minutes` from the session file. Photos uses that field as the asset date. A HEIC encoded now sorts as today. The match window is also the NAS mtime: `prove_nas_raw` records `modified_unix_seconds`, discovery stores that as `source_captured_unix_seconds`, and the default tolerance is 2 seconds (`DEFAULT_CAPTURE_TOLERANCE_SECONDS`). Send the original record's `assetDate` (already parsed in `parse_cloudkit_asset_record`) as `lastModDate`, and keep the EXIF copy. Do not use the session timezone as the photo's timezone.

## (e) Staleness

Live truth is the per-zone change token. The manifest is a cache of work, keyed by record id, and it is allowed to be behind only until the next sync.

What drifts today:

- The work list is a directory walk. iCloud can gain, delete, or move an asset and the manifest will not notice until a path appears or a later proof happens to re-check.
- `State::allows` only moves forward. `source_age_proof_is_frozen` freezes the mtime-as-capture-date once the asset is eligible, approved, failed, or terminal.
- The local mirror copies the HEIC into the icloudpd tree (`ensure_icloudpd_local_mirror`) and never removes the RAW. The NAS grows. That is fine only if the NAS is a cache and the index is the authority.
- `record_change_tag` is snapshotted at resolve time and reused for delete. A mismatch failing the modify is the correct fail-closed behavior. Do not fetch a fresh tag and retry `isDeleted` automatically.
- Hidden and deleted assets are excluded by the query name `CPLAssetAndMasterByAssetDateWithoutHiddenOrDeleted`. A changes feed is what sees a delete or a library move. The nightly full query is the repair when the token is rejected, not the thing that runs every scan.

Derived state, in order: zone change token, then record, then resource list, then local hash of bytes you actually have, then HEIC hash, then uploaded record id, then readback hash. Anything that cannot be rederived from those is a cache and can be dropped.

## (f) Correctness holes

Ranked by how badly they lose or duplicate photos. `auto_delete` is false, so the delete holes are latent. They become live the moment that flag is turned on. Do not turn it on to test them.

1. **Deleting the asset deletes every resource on it.** `cloudkit_delete_payload` sets `isDeleted` on the `CPLAsset`. icloudpd stores one file per asset. The paired RAW on `resOriginalAlt` (or a sibling RAW field) is not on the NAS, is not in the manifest, and would be destroyed with the asset. No delete candidate until every RAW-typed resource on that record has a local SHA-256. This is C2, and it is a safety precondition, not a throughput item.

2. **The monitor approves its own deletes.** `prepare_delete_item` writes eligibility and approval in one call. `BASE_DELETE_PLAN_PROOFS` does not include `remote_readback`, and `validate_pre_delete_facts` does not require it. The two execute paths (`workflow_delete_execute`, `delete_original_assets`) do download the HEIC and compare SHA-256 via `resolve_uploaded_heic_asset` immediately before modify. That live check must stay, and the stored `remote_readback` proof must become a precondition of any delete, so a later caller that only checks `DeleteApproved` cannot skip it. Approval itself moves to the expiring file. A missing or expired file means no request is sent.

3. **A crash between `putAsset` and `record_upload_proof` uploads again.** State stays `ConversionVerified`. `ensure_upload_dispatch_allowed` refuses only when an upload proof already exists. The next pass mints a new upload UUID. `operation_hold` is applied from the CLI (`apply_operation_hold`), not when a rolling upload times out. `run_rolling_asset_upload` does not hold the asset on a network error. Write the intent before the call. On any error after `createUploadUrl`, hold the row until a lookup in that zone either adopts the asset or proves it is absent. Adopting a 409 is not enough on its own.

4. **Wrong library, or no library, for shared originals.** One zone-bound read session. Shared 421s. The rolling path does not treat 421 as fatal, so it keeps going. Private and shared must be two queries on one session, and the row records which query produced it. Do not guess the zone later from a NAS path.

5. **Identity by mtime ± 2s plus a full re-download.** Two bursts in the same second become one cohort (`OriginalAssetTargetIndex`). Unique SHA-256 saves you from a wrong match, at the cost of downloading the RAW again, and a non-unique result becomes `OriginalAssetResolveNotUnique` and the file stalls. Record id does not have this collision.

6. **429 / 503 / 413 are the same error as a generic HTTP failure.** No backoff, so a raised cap will stampede. One classifier, as in (c). 413 must not be retried as if it were a blip.

7. **`record_change_tag` reuse is safe only because failure does not retry.** Keep that. A "helpful" refresh-and-retry of `isDeleted` is how a changed asset gets deleted on a stale decision.
